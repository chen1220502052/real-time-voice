# 实时语音系统测试报告与验收 Checklist

## 1. 测试结论

当前系统属于“可内部演示的 MVP”。基础链路、协议处理和资源清理表现良好，但实时性、异常恢复、麦克风状态反馈以及真实声学场景覆盖仍有明显缺口，暂不建议直接认定为生产级实时语音系统。

本报告区分以下三类结论：

- **已自动验证**：由自动化测试或 WebSocket 稳定性脚本验证。
- **已浏览器验证**：在当前浏览器和正在运行的真实服务实例上观察得到。
- **待人工听测**：依赖真实麦克风、扬声器、声学环境或主观音质判断。

## 3. 已发现问题

### 3.1 P1：建议优先修复

#### P1-01 麦克风失效时页面状态具有误导性

- **现象**：浏览器通话约 39 秒期间，上行包始终为 0，麦克风音量为 0%，但页面持续显示 `Active / 正在通话`，没有明确提示麦克风尚未启动或权限仍在等待。
- **位置**：`web/app.js::startMicrophone`、`activateSession`。
- **原因**：`getUserMedia()` 没有超时；会话在麦克风真正开始采集前就进入 Active；页面没有独立的麦克风状态机或“持续零上行”看门狗。
- **影响**：用户会误以为系统正在听，实际上服务端没有收到任何声音。
- **建议**：
  - 增加 `RequestingPermission / Capturing / Muted / Failed` 麦克风状态；
  - 为 `getUserMedia()` 和 AudioWorklet 初始化设置超时；
  - 建会后若 2～3 秒仍无 `microphone_started` 或上行包，显示明确告警；
  - 区分“静音”和“没有采集设备/没有上行”。

#### P1-02 LLM/TTS 异常后 Reply 状态可能无法收敛

- **位置**：`backend/duplex.py::_reply_worker`。
- **现象**：LLM、TTS 或播放异常时只产生错误事件，没有统一清除当前 Reply、媒体缓存和机器人状态。
- **影响**：`activeReplyId` 以及前端机器人状态可能永久停留在 `Thinking` 或 `Synthesizing`；如果用户不继续说话，会话不会自行恢复。
- **建议**：新增统一的 `fail_reply()` 路径，使 epoch 失效、取消关联任务、清理旧媒体、恢复机器人 Idle，并产生 `reply_failed` 事件。
- **必测项**：分别注入 LLM/TTS 错误，确认报错后同一会话仍可成功完成下一轮。

#### P1-03 Piper 取消不等于底层推理停止

- **位置**：`backend/atomic.py::PiperTts.stream_pcm`。
- **现象**：取消等待同步执行器的异步 Task 后，底层 Piper 推理线程仍可能继续运行，而协程锁可能提前释放。
- **影响**：连续插话时，新旧 TTS 可能同时占用 CPU 或并发访问同一个 voice，导致资源堆积和线程安全风险。
- **建议**：为 Piper 使用专用单线程执行器或可终止的独立工作进程；在旧合成真正退出前，不允许同一 voice 开始下一次合成。
- **必测项**：使用不可立即取消的同步 TTS Stub 连续打断，断言最大并发合成数为 1，后台任务最终归零。

#### P1-04 浏览器上行缺少发送背压

- **位置**：`web/app.js::sendAudio`。
- **现象**：每 100 ms 直接调用 `WebSocket.send()`，未检查 `socket.bufferedAmount`。
- **影响**：网络或后端变慢时，过期语音会在浏览器持续积压；后端有界队列无法限制浏览器内存和端到端延迟。
- **建议**：设置约 1 秒的上行积压阈值；超过阈值时采用明确的丢弃策略，并记录 `uplink_backpressure` 或 `queue_overflow` 事件。
- **必测项**：模拟高 `bufferedAmount`，确认过期音频停止发送，同时控制消息仍可优先发送。

#### P1-05 建会关键阶段缺少超时

- **位置**：`web/app.js::startCall`、`startMicrophone`。
- **现象**：WebSocket 连接、`prepare`、`create_session` 和麦克风初始化没有独立超时，仅挂断流程有超时兜底。
- **影响**：服务端不响应或浏览器权限请求长期悬而未决时，页面可能一直停留在连接中或表面 Active。
- **建议**：为每个阶段设置独立超时和错误码，并保证失败后释放 WebSocket、麦克风、AudioNode 和后端资源。

### 3.2 P2：正确性与体验问题

#### P2-01 TTS 首包指标可能不准确

- **位置**：`web/app.js::rememberMetric`。
- **现象**：同一 Turn 中后续 `tts_segment_started` 会覆盖首段时间，而 `tts_first_audio` 保留第一次时间。
- **影响**：TTS 首包耗时可能显示成 0 ms，掩盖真实延迟。本轮浏览器实测即显示 0 ms。
- **建议**：首包指标只保存第一次事件；各 TTS 分段使用 `segmentIndex` 分开记录。

#### P2-02 极短语音可能缺少 Turn 关联

- **位置**：`backend/duplex.py::_decode_audio`。
- **现象**：如果 ASR 在第一包直接返回 `status=3`，此前可能尚未建立 `_active_user_turn_id`。
- **影响**：`speech_ended`、`asr_final`、用户历史和机器人 Reply 无法稳定关联到同一个 Turn。
- **建议**：处理任何 `status in {1, 2, 3}` 的语音事件前，保证当前 Turn 已存在；完成全部写入后再清空。

#### P2-03 输入队列默认可积压约 6.4 秒

- **位置**：`backend/duplex.py::DuplexDialogue.__init__`。
- **现象**：默认输入队列为 64 个 100 ms 音频包。
- **影响**：慢 ASR 场景中，字幕、端点和打断最多可能落后数秒，偏离实时对话目标。
- **建议**：默认限制在约 10 包，即约 1 秒；采用“丢旧保新”或明确的实时优先策略，并确保控制事件不被音频挤占。

#### P2-04 30 分钟稳定性门禁不是真正的连续通话测试

- **位置**：`scripts/stability_test.py`。
- **现象**：脚本反复创建短会话，每个会话仅发送 3 个音频包后关闭。
- **影响**：可以证明连接 churn 和清理能力，但不能证明单会话连续运行 30 分钟时无队列增长、无串轮、无内存或线程泄漏。
- **建议**：保留现有脚本作为 `session_churn_test`，另建 `long_session_test`，在单一 WebSocket 中持续发送音频、制造多轮回复和插话，并周期采样 RSS、线程、任务数和各队列深度。

#### P2-05 真实 ASR 门禁（已关闭）

- **已关闭的本地路径**：新增可重复生成的 16 kHz 中文 WAV fixture；本地
  FSMN-VAD + Paraformer 产生完整状态并识别为“你好请问有什么可以帮助我的”。
- **已关闭的云端路径**：保持应用 WebSocket 100 ms 协议不变，在 NLS 适配层
  按 SDK 推荐拆成 20 ms 写入；同一 fixture 已获得非空 final。
- **仍需人工复验**：使用真人麦克风检查实际房间噪声、口音与回声环境下的效果。

#### P2-06 缺少自动重连和设备变化处理

- WebSocket 意外断开后没有自动重连或可配置重试；
- 未监听网络在线状态变化；
- 未监听 `devicechange`、麦克风 track ended、系统切换输入设备等事件；
- 蓝牙耳机切换、浏览器后台挂起和 AudioContext suspended 尚无恢复逻辑。

#### P2-07 浏览器实时播放缺少可重复自动化门禁

- 当前 Python 测试无法覆盖浏览器 AudioContext 调度；
- 尾包 flush、预缓冲、underrun、旧 epoch 丢弃和打断计时器清理主要依赖人工观察；
- 建议增加浏览器自动化，通过可控 WebSocket 和音频时钟验证上述路径。

#### P2-08 Python 3.13 音频转换兼容性（已关闭）

- 已移除 `audioop` 依赖，改为项目内 PCM16 单声道线性重采样函数；
- 已增加采样时长、恒定波形和畸形负载测试，消除该项 Python 3.13 阻塞。

#### P2-09 开场白文案错误

- 当前文案：“您好，我是猫猫，您有什需要帮助的吗”。
- 建议文案：“您好，我是猫猫，您有什么需要帮助的吗？”
- 应同步修改代码、README 和相关测试断言。
